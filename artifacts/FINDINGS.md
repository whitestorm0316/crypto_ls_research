## A. 策略定义与经济假设（Q1–Q4）

### Q1. 策略到底是怎么定义的？给出可直接复现的规格。

`v3` 定稿配置（`artifacts/v3/tables/00_run_meta.json`、`OPTIMIZATION_RESULTS.md §1`）：

```
标的池      OKX USDT 永续，instCategory == 1（纯加密）→ 134 个（总 161，剔除 23 股票/ETF + 4 商品）
            PIT 门槛：上市满规定时间 + 滚动 24h 成交额 ≥ $3M → 可交易池 10–22 个名字
因子        range_pos（区间位置）、hitrate（上涨持续性）—— 2 因子 z-score 等权合成 score
排序/选币   |score| 排序取 Top-K 多 + Top-K 空，K = 10，且 |score| ≥ min_abs_score
权重        |score|/vol 反向波动率加权 + 单名字上限 max_weight_per_instrument = 0.20
beta 中性   B 法（真 beta 中性，对 BTC 收益回归后逐日调整）
调仓        每 3 天（72 bar）
换手约束    日换手预算 20%（比例分配）
执行价      next_open（信号 bar 的下一根开盘）
资金费      真实拼接 126/161（OKX 实测 + 币安历史回填）
```

复算命令见 `OPTIMIZATION_RESULTS.md §1`，一次约 40 分钟（含 `--stages mc`）。

**为什么 K=10 / cap=0.20 不做改动**：`cap × K = 0.20 × 10 = 2.0 > 1`，sizing 真正生效。  
K=5 时 `cap × n = 1.0` 恰好卡在退化边界，**100% 的调仓退化为等权**——  
那个"增益"的一半是「5 个名字等权」的红利，不是「书更窄」的红利（`OPTIMIZATION_RESULTS.md §3.5`）。

### Q2. 策略名字所暗示的经济假设成立吗？

**部分不成立，而且这是本报告最重要的发现之一。**

策略叫「流动性流向 × 趋势」，但：

| 因子                | 推荐参数下的贡献     | 备注                              |
| ----------------- | ------------ | ------------------------------- |
| `range_pos`（区间位置） | 最强单因子        | 与 `momentum` 相关 **0.716**（高度冗余） |
| `hitrate`（上涨持续性）  | 次强           | 与 `range_pos` 组合最佳              |
| `momentum`        | 冗余，已被剪掉      | ρ=0.716 → 剪掉后 +0.371 Sharpe     |
| `flow`（流动性流向）     | **最弱**（但非无效） | 单独 0.542                        |

> **真实 alpha 是「长周期横截面均值回复 / 区间位置效应」，而不是「流动性流向趋势」。**  
> Flow 不是无效因子（推荐参数下 +0.542；默认参数下的负值是**成本**造成的，不是没有信息），  
> 但它**不是**收益的主要来源。

### Q3. 所谓"市场中性"是真的中性吗？

量化回答（`v3/tables/01_headline_metrics.json`）：

| 指标             | 值            |
| -------------- | ------------ |
| 净敞口均值          | **0.0242**   |
| 平均总敞口          | 0.4649       |
| beta 敞口均值      | **−0.00267** |
| beta 敞口均值（绝对值） | 0.0309       |
| beta 敞口标准差     | 0.0446       |

**是的**——美元方向敞口 2.4%、beta 敞口 0.27%，且 5.73 年内稳定。  
但要做到这一点是有代价的：真 beta 中性（B 法）Sharpe 1.9373，而毛敞口匹配（A 法）是 2.0482，  
**多花约 0.11 Sharpe 换取真正的 beta 中性**。选择在 B 法。

### Q4. 是预测 BTC 方向吗？

**不是。** 这是一个**池内横截面**策略：每天都在判断「同池子里哪个币相对强/弱」，  
而不是判断加密市场整体涨跌。上表的 beta 敞口 0.0027 就是这条的证据。  
`FINAL_REPORT.md §8.6` 另有独立性证据：剔除 BTC 后净 PnL 反而略升（0.4472 → 0.4709）。

### Q6. 资金费数据怎么处理？覆盖多少？代理误差多大？

**这是全项目最值得单列的数据议题。**

- OKX 公开接口 `/api/v5/public/funding-rate-history` **只保留约 3 个月**（BTC 实测最早 2026-06-22，  
  再往前翻页返回空）→ 若只用 OKX，**95% 样本上资金费 = 0**，会静默粉饰一个市场中性策略的成本。
- 因此用币安 `fapi/v1/fundingRate`（完整历史）回填。币安多数合约结算周期已从 8h 改为 4h/1h，  
  结算费率是「**每周期**费率」，故按 8h 窗口**求和**（不是取均值）才与 OKX 等价。
- **覆盖率真相**：第一轮只有 38/161 是真拼接，其余全是中位数代理；加大限流重试后续跑到  
  → **真实拼接 126/161，代理降到 35**。修复后**资金费 P\&L 由 −1.11%（净支出）翻为 +2.06%（净收取）**。
- **不可消除的代理误差**：OKX 与币安同一合约同一时刻的资金费**相关系数仅 0.63（中位 0.67，p10 0.32）**，  
  水平差 −0.52 bps/8h ≈ **−0.57%/年**。
- **影响边界**：资金费 ×0/×1/×1.5/×2 的敏感性阶梯下，Sharpe 落在 0.588–0.703 区间（非单调）  
  → **资金费假设不是结论的一阶驱动项**，它是二阶项。

> **判据陷阱（已修）**：覆盖率必须用「币安历史**是否真的取到**」（`real_splice` 集合）  
> 来界定，**不能**用「找到币安符号」。旧版因此把 124 个只有代理值的合约错标成 `okx+binance`。

### Q7. PIT 池为什么只有 10–22 个名字？这是不是缺陷？

**这是策略的结构性约束，不是疏忽，但它确实是外推风险的主要来源。**

- 流动性门槛 `$3M`（滚动 24h 成交额）在 2021–2026 的大多数时点只筛出 **10–22 个可交易名字**。
- *曾经试过放宽到 `$1M` 宽池：宽池在其****最佳频率****（7d）也只有 Sharpe 1.007 / 回撤 −14.5%，  
  仍低于窄池 3d + 20% 预算的&#x20;****1.279 / −9.49%****&#x20;→&#x20;****宁可窄而深，不要宽而浅****。*
- 后果有三条，都必须在汇报时披露：
  1. **分散度低** → 见 Q18（集中度）；
  2. **承受不了任何横截面宽度假设** → 见 Q22（因子中性化为何是灾难）；
  3. **在流动性危机中池子会急剧收缩**，而这个收缩本身是不可预测的。

### Q8. 非加密合约（代币化股票 / 商品）怎么处理？

`v3` 用 `--asset-class crypto` 剔除。发现过程中的一个教训必须写下来：

> 起初手写的剔除名单是 **34 个**，用 `instCategory` 权威字段重算是 **27 个**（23 equity + 4 commodity）。  
> **手写名单是错的。** 判据必须是「集合运算 + 权威字段」，且无法分类时**抛错**而不是静默缩池  
> （`crypto_ls_research/data/asset_class.py`）。

注意：这项改动带来 +0.285 Sharpe，但 **2021–2024 两组结果逐字节相同，全部增益来自 2026**  
→ 定义是**正确的**，但**尚未跨期验证**，因此标注为「中等信心」。

## C. 统计显著性（Q9–Q13）

### Q9. 【required】策略是否跑赢每一个随机零假设？

> ## **是的。真实策略在全部三个随机零假设下，都跑赢了 100% 的随机基准（百分位 = 1.00），且均达到 p < 0.05 的显著性。**

三个零假设（`v3/tables/22_montecarlo_summary.json`，共 430 个 placebo）：

| 检验         | n   | 真实 Sharpe  | 安慰剂均值   | 安慰剂标准差 | p05 / p95       | **p 值**      | **百分位**  |
| ---------- | --- | ---------- | ------- | ------ | --------------- | ------------ | -------- |
| 横截面置换      | 200 | **1.9373** | −0.1808 | 0.5032 | −0.903 / +0.617 | **0.004975** | **1.00** |
| 随机打分       | 200 | **1.9373** | −0.3750 | 0.4682 | −1.129 / +0.409 | **0.004975** | **1.00** |
| 分块打乱（保自相关） | 30  | **1.9373** | −0.3536 | 0.3366 | −0.790 / +0.172 | **0.032258** | **1.00** |

CAGR 维度同样显著：真实 25.09% vs 安慰剂均值 −1.01% / −2.25%，p = 0.004975。

**一个必须一并说明的观察**：安慰剂平均 Sharpe 是**深度负值**（−0.18 至 −0.38）。  
这不是噪声，而是**成本在起作用**——随机多空组合在高换手下必然被手续费与冲击成本磨死。  
真实组合能到 +1.94，说明其横截面排序信息足以**克服这条成本基线**，同时也说明  
**任何不做"""零假设对比"""的回测在这个资产类别里都会系统性高估自己。**

> 资金费符号修正对本条结论**无影响**：三个 p 值修正前后逐位一致（0.005 / 0.005 / 0.032），  
> 因为真实组与安慰剂组跑在同一个引擎里，符号同时作用于两者。

### Q11. 逐因子看，谁在赚钱？

因子消融吃饭的地方（`OPTIMIZATION_RESULTS.md §3`）：**因子集从 4 个瘦身到 2 个，是最大的单项改动，值 +0.371 Sharpe。**

被剪掉的两个：

- `momentum`：与 `range_pos` 相关 **0.7159**（`v3/tables/14_factor_correlation.csv`），纯冗余；
- `flow`：相关矩阵里与 `hitrate` 仅 0.202、**信息含量最低**，单独跑（默认参数）−0.040。

> **重要更正（曾写错过一次）**：因子结论**必须与实现参数一起报告**。  
> 同一组消融在默认参数下 `hitrate` = −0.344 / `flow` = −0.040，  
> 换到推荐参数后变成 **+1.202 / +0.542**。  
> 所以「单独为负但 IC 显著为正」时，**先怀疑成本与换手，而不是先怀疑因子**——IC 里不含成本。

### Q13. 样本外成立吗？

**——这是我要求删掉"逐年递增"这个漂亮措辞的地方。**

| 检验                     | 结果                                                         | 诚实解读                          |
| ---------------------- | ---------------------------------------------------------- | ----------------------------- |
| 走向前 4 折（test Sharpe）   | 1.446 / 1.948 / 2.498 / **3.686**                          | 全为正、且 test > train（−1.101 衰减） |
| **细化为 15 个季度折**        | **14/15 为正（93%）**，中位 2.141、最低 **−1.041（2024Q3）**、std 1.866 | 有整整一个季度是负的                    |
| **锁定样本（2026，不参与任何选择）** | Sharpe **3.686**、CAGR 75.64%、MDD −5.57%、6,432 bar          | **最强的证据恰好来自最不典型的一段**          |

**别把 ✅ 读过头**：4 个年度折"全为正且逐折递增"是**折数太粗**造成的乐观印象。  
细到季度后 2024Q3 是 −1.041；季度 Sharpe 的估计噪声本来就大（每折仅 63 个交易日）。  
**"93% 为正"和"某一季为负"可以同时为真。**

另外一条判据规定写在这里：**季度折的正向占比是低功效统计量，不可用作门禁**；  
年度 / 改动判据是「正向占比 ≥ 2/3 + 单年不超过 Σ|Δ| 的 35% + 锁定样本同号」。

### Q22. 有哪些看起来该做、实测被证伪的？

**这一节的价值不低于上面任何一条。** 五个「不做」全都有证据：

| 候选改进 | 预期 | 实测 | 判定 |
|---|---|---|---|
| **因子中性化**（brief §38 明确要求的一步） | +5~15% | **−0.34 ~ −1.41 Sharpe**（4 因子 1.567 → **0.217**） | **不采用** |
| **多周期反转 book** | 负相关=分散化 | 毛 Sharpe 每个 horizon 都为负（−0.57~−0.98）；混合 45 格最佳权重**全为 0.0**，即便相关 −0.45 | **不采用** |

**调仓间隔实测（2026-09-28 记录值，同一面板、只改 `--rebalance-days`）—— 这是那一天的记录，
不是当前真值：**

| 调仓间隔 | Sharpe | CAGR | MDD | 回撤天数 | 年化波动 | Sortino |
|---|---|---|---|---|---|---|
| 1 天 | 1.8552 | 33.51% | **−16.79%** | 245.8 | 16.26% | 2.935 |
| 2 天 | 1.7536 | 25.42% | −15.48% | 409.8 | 13.39% | 2.740 |
| **3 天（当日交付口径）** | **1.9348** | 25.04% | **−12.72%** | 245.9 | 11.89% | 2.972 |

1 天调仓**净收益更高**（CAGR +8.5pp），但**风险调整后更差**：每单位收益要承担 37% 更多的波动，
回撤深 4.1pp。这与 IC 形状一致 —— 4h IC **−0.0227**、7d IC **+0.0325**：**信号本身是慢的**，
日频调仓主要是在为噪声付手续费。日均换手上限 20% 在 1d 网格下几乎每期吃满，
调仓总次数约为 3 天档的三倍。

> **不要只看 CAGR 就把间隔改到 1d。** 更高的年化来自更高的波动（更接近满仓），
> 不是来自更好的选币 —— Sharpe 与 Sortino 都给出了同一个方向的答案。

**复核（2026-09-29，两档跑在**同一个面板**上：50,332 根 bar × 140 个合约，末根 2026-09-29，
只有 `--rebalance-days` 不同）：**

| 调仓间隔 | Sharpe | CAGR | 最大回撤 | 回撤天数 | 年化波动 | Sortino | 年换手 | 成本拖累 | 调仓次数 |
|---|---|---|---|---|---|---|---|---|---|
| **1 天** | **1.8215** | **32.53%** | **−16.79%** | 244.9 | 16.13% | 2.916 | **70.23** | 6.05% | 2068 |
| 3 天 | 1.7627 | 21.30% | −7.57% | 156.4 | 11.30% | 2.763 | 23.92 | 2.59% | 690 |

**上表的排序不复现，而且翻转了**（记录：1 天 1.8552 < 3 天 1.9348；实测：1 天 1.8215 > 3 天 1.7627）。
**复现的是定性结论、不是排序**：1 天档回撤 **2.22 倍**深、年换手 **2.94 倍**、成本拖累 2.33 倍、
平均毛敞口 1.36 倍（0.641 vs 0.470）。

**所以改判的理由不是「1 天更优」**，而是**口径必须描述真的在跑的那套配置**：守护进程按 **1 天**
网格下单，而验收 headline 一直报的是 3 天 —— 数字再好看，报的也不是在跑的东西。
风险调整后的差距（+0.059 Sharpe）远小于风险的差距（2.22 倍回撤），
**「1 天更优」这句话没有被证实**；被证实的只是「它换来了 +11.2pp CAGR，代价是 2.2 倍回撤」。

> 验收口径自 2026-09-29 起 = **1 天（`v4_1d`）**，3 天（`v3`）的产物留在盘上作对照。
> 引用任何一边的数字，**两个数必须一起报**（`/api/spec` 的 `optimal_headline` 与
> `optimal_cli.rebalance_days` 是唯一来源）。

> **因子中性化特别值得记一笔**：它是 brief §38 明确列的流程步骤，一度被记为
> "未实现的正经改进项"。实现后测得的结果说明，**在只有 ~16 个名字的横截面上回归掉 3 个噪声元，
> 吃掉的自由度远大于它提供的信息**。正解是**剪掉冗余因子，而不是把它们正交化**。

### Q23. 「看着像免费午餐」的通用破绽在哪？

本轮定了三条方法论硬规则，比任何一个具体结论都值钱：

1. **平台判据先看 argmax 是不是在网格端点**。边界点的邻域是单边的，
   单边邻域**分不清「宽顶」与「单调下降」**——曾经因此把"拒绝这个 overlay"报成"稳定最优"。
   现已加 `at_boundary`：**边界最优一律 `plateau = False`**。
2. **参数扫描撞上机制边界时，你扫的是机制开关不是参数**。
   若某点能让 `cap·n` 恰好 = 1.0，它常常就是 argmax，**而且每次都长得像真实增益**。
   → **报任何参数对比必须同时报「机制失效占比」。**
3. **两组只有 cap 不同的回测若 md5 相同，那就是「机制没生效」的最强信号。**
   （sizing 静默退化为等权这个 bug 就是这么被抓出来的。）

## G. 实盘就绪度（Q29–Q33）

### Q29. 实盘需要多少钱？能用杠杆吗？

`OPTIMIZATION_RESULTS.md §16` 的实测：

| 投入 | 结论 |
|---|---|
| **$70** | 能开仓，但每期 13 个有效名字只有 9 个落得下、**74% 的「名字×期数」被交易所最小下单量吃掉** → **下单粒度噪声大于信号本身** |
| **$500** | 信号覆盖率 **98.6%** —— 这是**最低可行门槛** |
| **$2,000–5,000** | ≥99.9%，接近回测口径 |
| 用 $70 + **4× 杠杆**补 | 有效 $280，**代价是 MDD 由 −12.7% 变 −42.9%** |

> **杠杆这一条务必讲清楚**：杠杆**不是收益放大器**，它同时放大回撤。
> 上面 −12.7% → −42.9% 是 3.4 倍回撤换取名义 allocated 能力，不是 3.4 倍收益。
> 前端已接 `max_leverage`（默认上限 5.0）与保证金模式，并有一道
> `check_plan(..., leverage=...)` 的硬闸门；**杠杆设置失败不会被静默吞掉**，会显式报错。

> **⚠️ 2026-09-29 复核：最后一行读错了。** "用 $70 + 4× 杠杆补" 里的杠杆指的是
> **敞口倍数**，不是**账户杠杆**。实测（同一信号、同一净值，只改 `set_leverage`
> 为 不设/1×/3×/10×）：\$70 上四行都是 **6 笔订单、\$5.50 名义额、39.3% 覆盖率**；
> \$1,000 上四行都是 **17 笔、\$195.86、97.9%**。**账户杠杆对订单大小零影响** ——
> `LiveEngine.build()` 把规模算在净值上（`build_plan(target.weights, acct["nav"])`），
> `set_leverage` 只用于交易所侧的维持保证金和 `check_plan` 的上限检查。
> 所以在 \$70 上"开 4 倍杠杆"**买不到任何保真度**，只把维持保证金压到 1/4。
> 要真的补，必须抬**敞口**（`risk.max_gross_exposure` / `max_gross_frac` /
> `max_gross_notional`），而那是另一条路径。详见 `OPTIMIZATION_RESULTS.md §16.5.1`。

> **⚠️ 2026-09-30 再补一刀（见 Q36）："保证金模式" 那一半也没咬。**
> `td_mode` 只是某个 `LiveEngine` 的内存属性：`LiveLimits` / `limits.json` / `fills.jsonl`
> 里**都没有它**，`AutoTrader` **从不传它** ⇒ 守护进程恒 `cross`，控制台可被一次请求改成
> `isolated` 且**重启即静默回 `cross`**；`liquidation_ok` 也**对模式完全不敏感**，而且读的是
> `rcfg.max_leverage` 而不是交易所上实际生效的 `lever`。实测 demo 账户因此变成**混合账本**
> （9 个合约同时持有两种模式），其中 `BTC-USDT-SWAP short` 的逐仓腿在 **100×** 上距爆仓 **0.58%**。

### Q29b. 生成的下单计划为什么说「下次调仓 3 天后」？（2026-09-29 已修）

**因为交易台与守护进程各读了一个网格。** 验收口径在 2026-09-29 从 3 天换到 1 天，
守护进程用 `--rebalance-days 1` 启动，但**交易台的计划路径**（`/api/live/plan` →
`LiveEngine.signal_kwargs`）取的是 `execution/engine.py::DEFAULT_SIGNAL`，
那里还写着 **`"rebalance_days": 3.0`**。于是：

* 守护进程：每天调仓；
* 控制台「生成下单计划」：`rebalance_bars = 72`、`next_decision_ts = decision_ts + 3 天`，
  连 `not_due` 警告的正文都写着「策略每 3 天调仓一次」。

**没有任何地方报错。** 页面不空白、不抛异常，只是每个数字都在描述另一套策略 ——
这正是"前端/另一层留了一份拷贝"这一类缺陷的标准长相。

修法是**一个来源**：`config.settings.ACCEPTED_REBALANCE_DAYS`（当前 1.0），
由 `execution.engine.DEFAULT_SIGNAL`、`auto_ctl.start` 的签名默认值、
`webapp.spec.OPTIMAL_CLI`、`scripts/auto_demo.py` 各自**引用**，
`check_plan` 的 `not_due` 文案也从目标自己的 `rebalance_bars` 派生
（`engine.grid_days()`），不再写死。

守卫测试 `crypto_ls_research/tests/test_accepted_grid.py`（13 条，9 个变异全部被抓）
断言的是**一致**而不是数值，所以下次**故意**改口径不会误红，改漏一处才会红。

### Q29c. 做空腿的 `side` 反了（2026-09-29 已修）

在生成上面那份下单计划时发现：`planner._orders_for_instrument` 的
**increase / reduce** 分支用 `abs(tgt_sz) - abs(cur_sz)` 推 `side`，把符号丢了：

```python
d = abs(tgt_sz) - abs(cur_sz)
legs.append(leg("buy" if d > 0 else "sell", ps, abs(d), ...))
```

`long_short_mode` 里 `posSide` 说的是**动哪个仓**、`side` 才是**方向**，
所以 **加空必须 sell**（减空必须 buy）。上面这一行对多空一视同仁地返回 `buy`，
于是**每一条加空的腿都变成了买入** —— 也就是在把空头买回来。

**它是静默的**：订单被交易所接受、不报错、计划看起来正常，只是仓位朝反方向走。

实测证据（修复前的 demo 账户）：

| | 多头 | 空头 |
|---|---|---|
| 个数 | 7 | 5 |
| 毛敞口 | **$9,431** | **$817** |

实际多头占比 **92.0%**，而策略目标是 **47.6%** ——
**这个"市场中性"策略在实盘路径上根本没有被当中性执行**。
PEPE/LIT/BTC/ETH 的空头只剩下 `-1.6 / -8.0 / -0.04 / -0.12` 这种残渣。

两个连带结论：

1. 之前把 demo 的低毛敞口（0.19× 净值）**全部归因于换手预算爬坡**是不完整的
   —— 空头那一半还在被这个 bug 持续买回来。
2. **demo 至今的成交记录不能当作策略演练**：它跑的是一个 92% 净多头的账。

修法与守卫：

* `d = tgt_sz - cur_sz`（带符号），`action` 用 `abs(tgt) > abs(cur)` 判；
* `crypto_ls_research/tests/test_order_sides.py`：**8 种仓位转移 × 2 个模式**
  的表驱动断言（含 flip 两腿），外加一条**性质断言** —— 把腿按成交方向走一遍，
  终点必须落在 `tgt_sz`（符号错误也能编出一张看着合理的表，所以要验性质）；
* 变异验证：把 `d` 改回 `abs()` 形式 → 恰好 4 条变红（加空/减空 × 两个测试）。
* 修复前 `_orders_for_instrument` **一条测试都没有**（全仓库 grep 无引用），
  这也是它能活到现在的原因。

### Q29d. 「$70 开 5 倍 = $350」到底该拧哪个旋钮？（2026-09-29 实测）

用户追问：「我用倍数也没法吗？比如 70 刀开 5 倍不就是 350 刀吗」。
算术没错，**旋钮全错**。有三个东西被叫做「倍数」，只有一个会改订单：

| 旋钮 | 是什么 | 实测（NAV=$70，同一引擎、冻结行情） | 结论 |
|---|---|---|---|
| **账户杠杆** `set_leverage` | OKX 侧的**保证金**设置 | 不设 / 5× / 10× → **6 笔 / $5.55 / 39.6%**，逐字段相同 | ❌ 不改任何一笔订单 |
| **目标敞口**（把信号权重乘 m） | 看起来最像「×5」 | m=2 / m=5 → **6 笔 / $5.55 / 39.6%**，逐字段相同 | ❌ **被节流等比抵消** |
| **策略节流** `execution.max_daily_turnover` | 每期允许多少换手（NAV 比例） | 0.2 → **6 笔/39.6%**；1.0 → **14 笔/93.1%** | ✅ 唯一有效的旋钮 |


**为什么放大目标也无效（这条最反直觉）**：换手预算是**净值的比例**。
目标权重乘 m ⇒ `turnover_wanted` 乘 m ⇒ `turnover_scale` 变成 `1/m`
⇒ 实际执行的书 `m·w·(scale/m)` **一点没变**。这是硬不变量，不是某个数字的巧合，
已由 `tests/test_size_invariance.py` 钉死（4 个变异全部变红）。

**那「$70 开 5 倍 = $350」在哪儿成立？** 只在一个地方成立：**保证金**。
`$70` 在 5× 杠杆下最多能持 `5 × 70 = $350` 毛敞口 —— 但那正好把保证金用光、
**剩余缓冲 $0**。所以它是**极限**，不是**能力**：

| 目标倍数 | 毛敞口 | 5× 杠杆占用保证金 | 占净值 | 10× 杠杆 |
|---|---|---|---|---|
| 1×（策略实际） | $74.27 | $14.85 | 21.2% | $7.43（10.6%） |
| 2× | $162.33 | $32.47 | 46.4% | $16.23（23.2%） |
| **5×** | **$385.14** | **$77.03** | **110.0%** | $38.51（55.0%） |

5× 那一行**建不起来**（保证金需求 > 净值）。而策略本身只要 `1.09× NAV`，
所以这个倍数对下单量**毫无帮助**。

**真正的等价关系**：不变量是「**净值 × 节流**」。实测
`$70 节流=1.0` 与 `$350 节流=0.2` **名义额 / 覆盖率 / 笔数完全相同**
（两边都是 70）。所以「$70 想当 $350 用」唯一成立的形式是**放开节流**，
而且它买到的只是**首期订单量**，买不到 $350 的**目标规模**
（目标恒为 `1.0887 × NAV`，$70 的目标就是 $76，开多少倍杠杆都不会变成 $381）。

**代价**：毛敞口/净值 决定能扛多少反向波动 ——
`1.09× → 91.9%`、`2.18× → 45.9%`、`5.44× → 18.4%`。
加密市场单日 18% 很常见。

> ⚠️ **放开节流 ≠ 免费午餐**：回测的 Sharpe 1.821 来自一本被节流到
> **0.472× NAV** 毛敞口的账；放开后立刻建到约 **0.93× NAV**，是验收敞口的
> **约 2 倍**。这是**换一套没验收过的配置**，指标不能照搬。

可复现产物：`scripts/plan_report.py --mode live` 第 **5 / 5b** 节
（含不变量自检，破坏即 raise）。

### Q33. 收益是**策略生效**，还是**市场好**？（2026-09-29 盲测）

「市场好」可以指三件完全不同的事，必须分开测。只做第一个，正是把 beta 书误当 alpha 书的原因。

#### 一、BETA —— 是不是只是加了杠杆的加密敞口？

把逐 bar 净收益回归到市场因子上（Newey-West HAC）：

| 序列 | 市场因子 | n | 年化 α | t(α) | β | t(β) | R² |
|---|---|---|---|---|---|---|---|
| **净收益** | BTC | 2067 | **42.73%** | **4.89** | −0.0158 | −1.56 | **0.0024** |
| **净收益** | 等权加密指数 | 2067 | **43.68%** | **4.96** | −0.0315 | −4.33 | **0.0216** |
| 净收益 | 等权（剔 BTC/ETH） | 2067 | 43.69% | 4.96 | −0.0314 | −4.35 | 0.0218 |
| 多头腿 | 等权 | 2067 | 13.68% | 1.87 | **+0.2582** | 19.04 | **0.6485** |
| 空头腿 | 等权 | 2067 | 31.88% | 4.29 | **−0.2904** | −17.58 | **0.7112** |

**市场只解释净收益方差的 0.2%–2.2%**，而 α 又大又显著。两条腿**各自**都是市场 beta
（R² = 0.65 / 0.71，β = +0.26 / −0.29），净额把它们抵掉了 —— 这就是市场中性书的教科书签名。

**结论对 HAC 带宽不敏感**：lags 从 0 扫到 48，净收益对等权市场的 t(α) 只在 **4.86–4.98** 之间
（`35c_market_bandwidth.csv`）。估计量本身用 AR(1) 合成数据对过移动块自助法：
`se_hac/se_boot` 在 lags=0/5/24/48 分别是 0.41 / 0.78 / **1.00** / 1.03。

⚠️ **但这一节不能单独作为结论**：β ≈ 0 是**构造出来的**（`net_exposure` 均值绝对值 0.051，
`beta_exposure` 均值 −0.0011），一个把 beta 钉死为 0 的构造让 beta 检验变成同义反复，
而不是发现。真正的可falsify 检验在下一节。

#### 二、LUCK —— 排序到底有没有信息，还是随便排都行？

三种置换零假设，各 200 / 200 / 30 次（`22_montecarlo_summary.json`）：

### Q34. 把这个策略**反着做**会怎样？（2026-09-29 实测）

**问题**：把信号想要做空的名字**买多**、想要做多的名字**做空**，其余一切不变。

**这是"收益是不是方向性的"最锋利的一刀**，而且结论**可以事先算出来**，不用等回测：

设 `net = gross − cost + funding`（本项目已把这条账本恒等式验到 ~1e-18）。镜像 book 持有
**同一批名字、同样的 |权重|、每条腿符号相反**，于是

```
gross_flip   = −gross        (同一本书，反方向)
cost_flip    =  cost         (同样的换手)
funding_flip = −funding      (空腿付出多腿曾收到的)
⇒  net_flip = −gross − cost − funding = −(net + 2·cost)
```

**镜像不但要亏，还要比原版赚的多亏一份成本。** 若镜像也赚钱，那原来的收益就不是方向性的。

#### 实现方式（决定这个比较是否成立）

`run_backtest(flip_book=True)` 翻转的是**装配好的目标权重**，位置在 `select_book` /
`build_units` / `side_gross_targets` **之后**，`base = -base`。

**不是** `score = -score`。因为 `_stable_book` 的留任缓冲是路径依赖的，取负分数会**连选股一起改**，
比较就被污染了。守卫 `tests/test_flip_book.py` 用**结构断言**钉住这个位置（行为断言做不到：
两种实现在单次调仓上完全一致，只在多次调仓后才分叉）。

#### 恒等式逐条验证（`36b_reverse_identity.csv`，逐 bar 最大绝对偏差）

| 恒等式 | 照做（风控开） | 纯镜像（风控关） | 纯镜像+零成本 | **纯镜像+零成本+关 ADV 上限** |
|---|---|---|---|---|
| `gross_flip == −gross_normal` | 3.60e−02 | **0.000e+00** | 5.76e−03 | **0.000e+00** |
| `long_flip == −short_normal` | 6.35e−02 | **0.000e+00** | 2.20e−03 | **0.000e+00** |
| `short_flip == −long_normal` | 3.26e−02 | **0.000e+00** | 5.98e−03 | **0.000e+00** |
| `turnover_flip == turnover_normal` | 2.00e−01 | **0.000e+00** | 1.35e−01 | **0.000e+00** |
| `funding_flip == −funding_normal` | 2.98e−03 | **0.000e+00** | 2.87e−04 | **0.000e+00** |
| `gross_exposure_flip == gross_exposure_normal` | 9.33e−01 | **0.000e+00** | 1.35e−01 | **0.000e+00** |
| `impact_flip == impact_normal` | 2.21e−04 | 1.12e−03 | 0.000e+00 | 0.000e+00 |
| `net_flip vs −(net_normal + 2·cost)` | 3.60e−02 | 1.12e−03 | 5.76e−03 | **0.000e+00** |

⚠️ **`long_ret` / `short_ret` 是按持仓符号取的带符号 P&L**（`long_ret = Σ held·(held>0)·r`），
所以镜像把 long 映到 **−short**。写成 `long_flip == +short_normal` 是最容易犯的那个错 ——
这张表在出报告之前先抓住了我自己写反的符号。

⚠️ **两处"精确"之外的东西，都因为读了 `equity`**：
* `impact_rate(delta, adv, **equity**, vol)` —— 两臂净值反向复利，participation 不同 ⇒ impact 不镜像
  （fee / spread 正比于 |delta|，**逐位精确**）。这条残差在聚合上**恰好等于**
  `Σcost_flip − Σcost_normal`（−0.218），恒等式因此完全闭合。
* `adv_cap_delta` 的 `scale = min(1, budget / (|delta|·**equity**))` —— 一旦某臂净值涨到上限咬住，
  持仓就不再是精确镜像。**把 ADV 上限调开后每一行都回到 0.000e+00**，这就是证明。

### Q35. 遇到**插针**（wick / 闪崩）会怎样？（2026-09-30 实测）

插针**同时是价格事件和信息事件**，而这两条通道的行为完全相反。第一版把结论写成
「回测看不见插针」，然后被自己的表打红：只放大影线（`high *= 1+w`、`low *= 1-w`，
open/close 一位不动）就改了 **32,558 根 bar** 的收益。原因不是收益口径，是**信号**：

```
range_pos = (close - low.rolling(180).min()) / (high.rolling(180).max() - low.rolling(180).min())
atr_pct   = ((high - low) / close).rolling(24).mean()
```

`high`/`low` 是 5 个验收因子之一 `range_pos` 的输入，也是 `atr_pct` 的输入。
按通道拆开量之后结论才干净（10 个 arm，`scripts/exp_wick_stress.py`）。

#### 通道 L —— 收益路径**只读 open**（逐位证明）

`exec_price="next_open"` ⇒ `ret_exec[t] = open[t+1]/open[t] - 1`。把影线注入到
**任何决策 bar 的回看窗都覆盖不到**的 bar 上（前 1 根 + 末 4 根），带风控与关风控两档：

| 量 | 逐 bar 最大绝对偏差 | 不同的 bar 数 |
|---|---|---|
| `net_ret` | **0.000e+00** | 0 |
| `gross_ret` | **0.000e+00** | 0 |
| `gross_exposure` | **0.000e+00** | 0 |
| `turnover` | **0.000e+00** | 0 |
| `dd_scale` | **0.000e+00** | 0 |

⇒ **插针「收回」时不产生任何损益**，不是「近似为零」。这条是逐位的，不是统计的。

#### 通道 S —— 插针是**信号信息**（这是真正的风险面）

全样本注入 300 根 bar（0.6%）的 30% 影线：

| arm | Sharpe | ΔSharpe | 期末净值变化 | 仓不同的 bar 占比 |
|---|---|---|---|---|
| 基线 | 1.9372 | — | — | — |
| 影线 30% | 1.7265 | −0.2107 | **−23.26%** | **94.70%** |
| 影线 30%·ATR×3 | 1.4934 | −0.4438 | **−45.98%** | 95.32% |

`range_days = 7.5` 天 = **180 根 bar**：一根宽 bar 把 `r_high`/`r_low` 撑开之后，
`range_pos` 被压扁**整整 180 根**。所以**一根坏打印能污染信号 7.5 天**，
而因子管线里**没有任何去刺（de-spike）处理**。

#### 通道 P —— 不收回的缺口 = 纯价格冲击，有解析式

`open` 在 `compute_factors` 里**从不出现**，所以只动 `open` 时**书逐位不变**
（注入点前逐 bar 毛敞口最大偏差 `0.000000`；选择与目标权重**全样本**逐位相同）。

⚠️ 一 bar 损益的解析式**不是** `w × Σheld`，而是 **`w × Σ held·(open[t+1]/open[t])`** ——
名义额按**被冲击后**的价格记，多一个价格比因子。写成 `w × 净敞口` 会差 0.03%
（−0.0086916 vs −0.0086939），是这张表抓出来的；换成正确形式后残差 **<2e-9**
（= float32 权重矩阵的精度）。

冲击点 2025-01-17 04:00Z（第 70% 个调仓的次根 open），该 bar 前净敞口 **+0.0869** / 毛敞口 **0.7815**：

| arm | 一 bar 损益 | 预测 | ΔSharpe | ΔMDD | 期末净值 |
|---|---|---|---|---|---|
| 全市场 open −10% | **−0.8694%** | −0.8694% | −0.0093 | **0.0000** | −0.89% |
| 全市场 open −20% | **−1.7388%** | −1.7388% | −0.0205 | **0.0000** | −1.90% |
| 单名 BTC open −50% | **−4.6186%** | −4.6186% | −0.0708 | **0.0000** | −6.08% |
| 单名 BTC open −90% | **−8.3135%** | −8.3135% | −0.1634 | −0.0023 | −13.18% |

**全市场插针被 beta 中性结构性抵消**：净敞口/毛敞口 均值 **0.0797**（p95 0.2049），
所以 −20% 的全市场闪崩只花 **1.74%** 净值，而不是 20% × 毛敞口。
**单名插针被 `max_weight_per_instrument = 0.20` 封顶**：BTC 实际权重 0.0924，
所以 −90% 花 **8.31%** 净值。

#### 爆仓距离（解析）与 ATR 门槛

全仓 `gross = G × NAV`、维持保证金率 `mmr = 0.005` ⇒ 同向移动 `m ≥ (1 − mmr·G)/G` 才爆仓：

| 毛敞口 / NAV | 爆仓所需同向移动 |
|---|---|
| 0.292（demo 当前） | **341.97%** |
| 0.468（策略中位） | 213.18% |
| 0.9636（目标） | 103.28% |
| **1.00（实盘上限 `max_gross_frac`）** | **99.50%** |
| 2.00（`risk.max_gross_exposure`） | 49.50% |

⇒ **在实盘上限 1.0× 净值下，账户爆仓需要整个组合同向移动 99.5% —— 结构性不可达。**
账户杠杆 5× 只决定维持保证金，不改敞口。

`liquidation_ok` 门槛 `3·ATR% ≤ 1/5 − 0.005 = 0.195` ⇒ **ATR% ≤ 6.5%**：

| 情形 | 通过 / 上市 | 通过率 | ATR 中位 | ATR 最大 |
|---|---|---|---|---|
| 实际 | **140 / 140** | 100% | 2.03% | 5.28% |
| ATR×1.5 | 136 / 140 | 97.14% | 3.04% | 7.92% |
| ATR×2.0 | 126 / 140 | 90.00% | 4.05% | 10.56% |
| ATR×3.0 | 83 / 140 | 59.29% | 6.08% | 15.84% |

⇒ **当前这道闸门完全不咬**（最差名字的 ATR 只有 5.28%，离 6.5% 还有余量）。
它在真正的高波动体制下才开始筛名字 —— 是**潜伏的**防御，不是当前的防御。

#### 历史极端（5.7 年真实发生过的最差单 bar）

| 量 | 最差 | 时间 | σ 倍数 |
|---|---|---|---|
| `net_ret` | **−4.257%** | 2024-03-05 04:00Z | −23.5σ |
| `long_ret` | −5.216% | 2021-09-07 14:00Z | −17.7σ |
| `short_ret` | −3.865% | 2025-10-11 02:00Z | −12.4σ |

⇒ 5.7 年里最坏的**一个小时**花掉 4.26% 净值。上面的「全市场 −20%」是这个的 **4 倍**。

#### 对照：已有的退市压力测试

30 次 × 每次注入 8 个 **−50%~−90% 单 bar 缺口 + 永久停牌**：
Sharpe **1.7469~2.0194**（中位 1.9216，基线 1.9372），`max_dd` **−11.3%~−19.4%**
（中位 −13.32%，基线 −13.31%）。⇒ **8 个名字同时归零也只让回撤从 −13.3% 走到 −19.4%。**

#### 结论：能扛住插针的价格，扛不住插针的**信息**

* **价格面是稳的**：影线不产生损益（逐位 0）；全市场闪崩被 0.0797 的净敞口抵消；
  单名闪崩被 0.20 的单名上限封顶；账户爆仓在实盘上限下需要 99.5% 同向移动。
* **信息面是不设防的**：一根宽 bar 污染 `range_pos` **180 根**，没有任何去刺；
  30% 影线打在 0.6% 的 bar 上就让 **94.7%** 的 bar 换仓、净值 −23.3%。
* **没有任何盘中动作**：无止损、无止盈、无算法单（`ordType` 只有 `market`），
  唯一的动作是**下一个网格点**（1 天）的调仓。

#### 顺带查出的四个缺口（都属于「屏幕上有、其实不咬」）

1. **`risk.dd_stop_new_entries_above` 是死字段的效果**：
   `backtest/engine.py:344` 写成 `ds, _stop = risk.dd_scale(...)`，`_stop` **从不被读**。

## 附录 — 一句话结论

> 在真实加密永续市场中，这个横截面市场中性策略**确实存在统计上可验证的 alpha**
> ——它跑赢了**全部三个随机零假设的 100% 安慰剂**（p = 0.005 / 0.005 / 0.032），
> 并且在 38 个参数配置下**全部正收益**；

> **Flow 是最弱的因子 —— 但不是无效因子**。
> 把调仓改为 1 天、换手预算降到 20%、并让 sizing 真正生效之后，

> **top-1 集中度从 41%（SOL）降到 11.2%** ——

> 收益**不是市场 beta**：与市场几乎不相关（R² 0.002–0.022）、α 年化 42.7% 且 t≈4.9（Q33）。
> **反着做是亏的，而且比原版赚的多亏一份成本**：5.7 年 6 个年度窗口**每一年都亏**
> （正常 +1.41~+2.63，镜像 −1.42~−3.47），纯镜像 Sharpe 精确反号（+1.7088 → −1.7088）（Q34）。

> （`ret_exec` 只读 `open`，偏差 0.000e+00），全市场闪崩被 0.0797 的净敞口抵消
> （−20% 只花 1.74% 净值），单名闪崩被 0.20 的单名上限封顶（BTC −90% 花 8.31%），

> 压扁整整 180 根**（7.5 天），0.6% 的 bar 带 30% 影线就能让 **94.7%** 的 bar 换仓、
> 净值 −23.3%，而系统**无止损、无去刺、无账户级回撤熔断**。
> **保证金模式必须钉成全仓 `cross`，不能做成可切换的选项**（Q36）：逐仓给每条腿
> `1/L − mmr` 的引信（3× → **32.8%**，100× → **0.5%**），全仓给 `(1 − mmr·G)/G`
> （当前 0.446 毛敞口 → **223.8%**），而**对冲腿的盈利在逐仓下救不了另一条腿**，
> 强平那一刻还会**把对冲拆成裸方向仓**。实测 demo 账户已经是混合的：
> **9 个合约同时持有两种模式**，其中 `BTC-USDT-SWAP short` 的逐仓腿在 **100×** 上
> **距爆仓 0.58%**，而同一合约的全仓腿距离 5,484% —— 差别**只来自保证金模式**。
> **而且那 100 倍不是下单造成的**（Q37）：`place_order` **不带杠杆字段**，杠杆是账户级配置
> `(instId, mgnMode, posSide)`；`_apply_leverage` 因 `set_leverage=None` 从不执行，
> **即使执行也设不上** —— `mgnMode=isolated` 不带 `posSide` 被 OKX **HTTP 400** 拒绝，
> `/account/batch-set-leverage` **404 不存在**。全账户两种模式默认 3×（连未碰过的合约也是），
> `BTC isolated = 100×` 是**遗留值**，订单把它原样继承；闸门仍按 19.5% 判断，**偏 33 倍**。
> **而"把逐仓杠杆统一设成 3×"救不了它**（Q38）：逐仓杠杆是 `(合约, 模式, 方向)` 的**独立配置格子**
> （`leverage-info` 返回 long/short 两条），改配置**确实会改 `lever` 字段，但不会重算已在场那条腿的
> `margin`/`liqPx`** —— 干净腿上实测 3→5：`lever` 变、`margin` 116.906 与 `liqPx` 3.317332 **逐位不变**
> （>65s 仍不变）。判断一条腿真正在几倍上只能从 `liqPx` 反推（`L ≈ 1/(|liqPx/mark − 1| + mmr)`）。
> 写杠杆还有四个坑：缺 `posSide` → **400**、`batch-set-leverage` → **404**、每合约要**两次**、
> **回读有几十秒延迟**（写完立刻读会骗你）。要真改只能**平掉重开**或**直接加保证金**。
> 代价与边界必须同时说：**退市偏差不可消除**（多头腿被高估，注入压力测试下 Sharpe 1.63–2.00）、
> **业绩集中在极端年份**（校准预期请用分年 Sharpe，不要用全样本；且 5 因子口径
> **锁定的 2026 段反而比 2 因子差**：2.740 → 2.172）、
> **高波动状态下基本失效**（HighVol Sharpe 0.118）、
> **池子只有 10–22 个可交易名字、峰度 8.71**。
> **换一家交易所的数据，策略活着但那个数字不活着**（Q40）：币安行情与 OKX 同 bar 收益相关
> **0.9944**、收盘价中位差 **4.6bp**，可头部指标是 **Sharpe 1.93 → 1.33、CAGR 39.0% → 20.1%、
> 空头腿 P&L 0.954 → 0.250** —— 差距**不在价格**，而在**成交额口径**：币安报的 USDT 成交额是
> OKX 的 **3.67 倍**，同一个 `$3M` ADV 门槛在 OKX 筛出 **16** 名、在币安筛出 **39** 名，
> **两边根本不是同一个策略**。把门槛按各自分位数扫、横轴对齐到实际宇宙规模后：
> 币安全程最高 **1.494**，够不到 OKX 的 **1.942**；而 OKX 那个 1.94 是**尖峰不是平台**
> （左右邻居 1.184 / 1.511），币安的线在宇宙 10–50 之间**平得多**（1.34–1.49）。
> ⇒ **1.94 至少部分是 (OKX 数据, 这个阈值) 的组合属性**；且关掉 ADV 门槛 OKX 从 1.93 掉到 **0.07**
> —— 结果高度依赖**一个宇宙阈值参数**。
> **在补全退市数据并完成 ≥3 个月纸面交易之前，不具备投入真实资金的条件。**

### Q36. 保证金模式要不要强制**逐仓**？（2026-09-30 实测）

**问题**：*"是不是要强制为逐仓，不然一个爆了全仓爆了？"*

**答案：对**独立方向性**的账本，这个直觉是对的；对这个**对冲过**的账本，它是**反的** ——
强制逐仓会把爆仓距离从 200%+ 缩到 30% 以内，并且**在爆仓的那一刻把对冲拆掉**。**

#### 为什么反了：一条不等式

| 模式 | 爆仓所需的同向移动 | 依据 |
|---|---|---|
| **逐仓 `isolated`** | `1/L − mmr` | 每条腿只用自己的保证金。`L=3` → **32.83%**；`L=5` → **19.50%**；`L=100` → **0.50%** |
| **全仓 `cross`** | `(1 − mmr·G)/G` | 全账户权益兜底，多空腿盈亏**互相抵消**。`G=0.4458` → **223.80%**；`G=1.0` → **99.50%** |

`mmr = 0.005`（`risk.DEFAULT_MMR`）。对任意 `L ≥ 1, G ≤ 1` 有 **`cross ≥ isolated`**，
唯一取等号的是 `L=1, G=1`（都是 `1 − mmr`）。守卫
`tests/test_margin_mode.py::test_cross_is_never_nearer_than_isolated` 在
`L ∈ {1,2,3,5,10,20,50,100,125} × G ∈ {0.05,0.29,0.44,0.96,1.0}` 的网格上逐点断言，
不靠代数。

**关键在于对冲腿的盈利救不了另一条腿**：逐仓下空头的浮盈躺在**另一个桶**里，
多头腿照样在自己的保证金耗尽时被强平。而这个账本的净敞口只有毛敞口的 8%
（回测均值 `net/gross = 0.0797`），所以市场整体 −20% 时账户净亏只有 **1.6% 净值**——
**账户毫发无损，但逐仓的每一条多头腿都会死**。更糟的是：一条腿被强平后**对冲就断了**，
剩下的那条腿变成**裸方向仓**，正好在剧烈波动中间。所以"一个爆了"不是逐仓**防止**的事，
而是逐仓**制造**的事。

#### ⚠️ 这不是假设 —— demo 账户已经是混合的（2026-09-30 10:57 实测）

1. **`td_mode` 不落盘、也没有唯一主人。** 它只是某个 `LiveEngine` 的内存属性：
   `LiveLimits` 里没有这个字段（所以 `limits.json` 里也没有），**成交记录里没有 `tdMode`**，
   而 `AutoTrader.__init__` **从不传它** —— 所以**无人值守的守护进程恒为 `cross`**，
   控制台却可以被一次请求改成 `isolated`，并且**控制台一重启就静默回到 `cross`**。
   实测：同一时刻**控制台报 `isolated`、同进程新建的引擎报 `cross`，同一个账户**。
   ⇒ 下一笔订单用哪种模式，取决于**哪个进程先提交**。
   ⇒ **已修**：模式收敛成唯一常量 `settings.MARGIN_MODE`（`cross`），
   `LiveEngine.td_mode` 是**只读属性**（赋值抛 `AttributeError`），
   构造时传冲突值抛 `ValueError`，`/api/live/*` 对冲突的 `td_mode` 回 **400**，
   控制台**不再提供选择器**（只读展示），运行记录带 `td_mode`。
   守卫 `test_the_margin_mode_cannot_be_assigned`、`test_a_conflicting_td_mode_is_rejected_not_ignored`、

   `test_the_console_offers_no_margin_mode_selector`、`test_the_run_record_carries_the_margin_mode`。
2. **`liquidation_ok` 对模式不敏感，而且读的是配置里的杠杆。**
   它算的恒是 `1/rcfg.max_leverage − mmr`（**逐仓口径**，`rcfg.max_leverage = 5` ⇒ 19.50%），
   既不看 `td_mode`，也不看交易所上**实际生效**的 `lever`。
   所以它可以一边认为"19.5% 很安全"，一边账户上躺着一个 **100×** 的逐仓仓
   （真实距离 **0.58%**，闸门**偏了 33 倍**）。
   ⇒ **已修（口径不变，假设显式化 + 实盘对账）**：字段改名 `RiskConfig.leverage_in_force`
   —— 它是**声明出来的建模假设**，不再是「上限被当成事实」；`liquidation_ok` 新增
   `leverage=` 显式覆盖；新增 `limits.margin_headroom_violations()` 拿每条腿
   `liqPx` 反推的**真实杠杆**与假设对账，结果进 `LiveEngine.status()["margin_headroom"]`。
   ⚠️ **公式仍是逐仓口径**：`cross` 下没有逐腿爆仓价，这个闸门本质是**波动率筛选**，
   不是账户偿付约束。改成按模式选公式会让它基本失效、**宇宙变宽、验收 Sharpe 变**，
   那是另一次（需要重跑验收的）改动，**本次刻意没做**。
   守卫 `test_the_gate_uses_the_declared_leverage_not_the_cap`、
   `test_margin_headroom_catches_the_100x_leg`、`test_margin_headroom_says_unavailable_rather_than_passing`。

**不要把保证金模式做成可切换的选项，把它钉成账户级常量 `cross`。**
理由不是"全仓爆仓更晚"，而是**这个策略唯一的系统性防线是 beta 中性，而 beta 中性只在全仓下成立**：
逐仓把"一个对冲账本"变成"9 笔独立的方向性押注"，每条腿 32.8%（3×）的引信，

### Q37. 为什么下单 BTC 之后 BTC 的保证金杠杆变成 **100 倍**？（2026-09-30 实测）

**答：不是下单把它变成 100 倍的 —— 它本来就是 100 倍，而这套代码从来没能改过任何一笔杠杆。**

#### 三条独立的证据

**① 订单里根本没有杠杆字段。** `place_order` 发的是
`{instId, tdMode, side, posSide, ordType, sz}`（`planner.Order.to_body`）。
OKX 的杠杆是**账户级配置**，键是 **`(instId, mgnMode, posSide)`**，**不随订单传**。
所以下单只会**继承**该合约在该模式下已有的杠杆 —— 这正是"下单后变成 100 倍"的错觉来源。

**② `_apply_leverage` 现在是空转的。** `set_leverage` 为 `None`（控制台没设）⇒
`if not self.set_leverage: return []` ⇒ **一次都不问交易所**。
证据：`artifacts/live/demo/runs.jsonl` 里 **6 次执行没有一次带 `leverage` 键**
（该键只在 `_apply_leverage` 返回非空时才写，`engine.py:711`）。

**③ 就算打开它，也设不上 —— 调用形状是错的（现场实测）。**
把每个值都设成它**当前已有的值**（等价 no-op，账户状态不变）：

| 调用 | 结果 |
|---|---|
| `mgnMode=cross`，不带 `posSide` | **200 OK** |
| `mgnMode=isolated`，不带 `posSide` | **HTTP 400 Bad Request** |
| `mgnMode=isolated`，带 `posSide=long` | **200 OK** |
| `POST /api/v5/account/batch-set-leverage`（带不带 posSide 都是） | **HTTP 404 Not Found** |
| `POST /api/v5/account/set-leverage` 传**数组** body | **HTTP 400** |

而 `okx_private.set_leverage()` / `set_leverage_batch()` **都不传 `posSide`**，
`set_leverage_batch` 还打在一个**不存在**的路径上。⇒ **在逐仓模式下，本项目永远设不上杠杆**：
单条调用缺一个 OKX 必需的参数，批量那条路整个不存在（每次都靠逐名回退，而逐名回退在逐仓下 400）。
顺带：在 long/short + 逐仓下杠杆是**按 `posSide` 分开**的，所以**一个合约要两次调用**
（long + short），21 个名字就是 **42 次往返** —— 大概正是当初想写"批量"的原因。

#### 那 100 倍到底哪来的

`/api/v5/account/leverage-info` 逐 `(instId, mgnMode)` 读回来：

`BTC-USDT-SWAP` 的 `isolated` = **100×** 是**唯一的例外**（也恰好是它的 `max_lever`）。
也就是说：这是**账户上早先被单独设过的一个遗留值**（不是在订单里产生的，
也不是本项目设的 —— 见证据 ②③），订单把它**原样继承**了下来。

**后果**：`liquidation_ok` 读的是 `rcfg.max_leverage = 5` ⇒ 闸门恒按 `1/5 − 0.005 = 19.50%`
判断，而这条腿的真实距离是 **0.50%**（含手续费实测 0.58~0.76%）—— **偏 33 倍，没有任何一处报警**。
`leverage-info` 还揭示了一个更广的问题：**只要某条腿被配成该合约的 `max_lever`，
它的爆仓距离就塌到 `1/max_lever`**，而闸门看不见。

### Q38. 逐仓的杠杆"能不能统一设成 3×"？（2026-09-30 实测）

**答：改配置能改，但它救不了已经在场的那条腿 —— 而 BTC 那条 100× 腿正是"已经在场"的。**

#### 先纠正问题的前提："逐仓倍数会变"其实不是"模式"在变

杠杆是**账户级配置**，键是 `(instId, mgnMode, posSide)`。也就是说**每个合约 × 每种模式 × 每个方向
各有一个独立的格子**。实测 `leverage-info` 返回的是**两条**记录（long / short 各一条），
证明它是**逐方向**的：

```
LINK-USDT-SWAP isolated = {'long': '3', 'short': '3'}
```

所以"切到逐仓倍数就变了"是**读了另一个格子**。全账户实测：

| | cross 格子 | isolated 格子 |
|---|---|---|
| 12 个持仓合约 + LINK/AVAX/ATOM 对照 | 全部 **3×** | 全部 **3×** |
| `BTC-USDT-SWAP` | 3× | **100×**（= 该合约的 `max_lever`） |

**BTC 的逐仓格子是唯一的例外**，而 100 正好等于 BTC 合约的上限。三个从未交易过的对照合约
也是 3× ⇒ 不存在"下单会把杠杆顶到上限"的机制。**它就是一个遗留的配置值。**

#### 能不能改？能 —— 但有四个实测的坑

在无持仓合约（LINK）和有持仓合约（ARB / NEAR）上都试过，**写入确实生效**：

```
LINK  isolated 3 → 5 → 3         ✓（每次回读都跟上）
ARB   isolated short 10 → 3      ✓
NEAR  isolated long  3 → 5       ✓
```

| # | 坑 | 实测 |
|---|---|---|
| ① | `mgnMode=isolated` **必须带 `posSide`** | 不带 → **HTTP 400**；带 `posSide=long` → 200 |
| ② | `POST /api/v5/account/batch-set-leverage` **不存在** | **HTTP 404**（数组 body 打 `set-leverage` 也是 400） |
| ③ | 一次只改**一个方向** | `leverage-info` 返回 long/short 两条；设 long 不动 short ⇒ **每合约要调两次** |
| ④ | **回读有几十秒延迟** | `set-leverage` 立刻回 200 并回显请求值，但 `leverage-info`/持仓的 `lever` 会继续显示旧值 |

⇒ 现在的 `okx_private.set_leverage()` 发的正是①的形状（带 `mgnMode`、**不带** `posSide`），
所以**逐仓杠杆在这个项目里从来没能被设上过**。

#### ⚠️ 最关键的一条：**改配置 ≠ 改持仓**

在一**条从未被碰过**的干净腿上做对照（NEAR isolated long，$350 名义，3×）：

```
before (clean)   config=3  pos.lever=3  margin=116.906  liqPx=3.317332  距离=32.44%
after 3→5 +65s   config=5  pos.lever=5  margin=116.906  liqPx=3.317332  距离=32.53%
                 ^^^^^^^^^^             ^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^
                 配置和 lever 都变了     逐位不变        逐位不变
```

**`lever` 字段变了，但持仓的 `margin` 和 `liqPx` 一模一样**（距离那 0.09pp 的变化来自 `markPx`
移动，不是爆仓价）。等了 65 秒仍不变。

> `lever` 只是**配置的镜像**，不是持仓实际被计价的杠杆。要读真相只能从 `liqPx` 反推：
> `L ≈ 1 / (|liqPx/markPx − 1| + mmr)`，即新增的 `audit_margin_mode.implied_leverage()`。

**所以「把杠杆统一设成 3×」不会把 BTC 那条腿变成 3×。** 要把一条**已开仓**的腿真正改到 3×，
只有两条路：

1. **平掉、按 3× 重开** —— 需要约 **$594** 保证金（$1,781 名义 / 3），而 100× 下只要 $17.85；
2. **直接给逐仓桶加保证金**（把爆仓价推远，但 `lever` 字段仍是 100）。

#### 实测产出：配置 vs 实际（`41f_config_vs_actual.csv`）

```
  ENA  long  config=  3x  实际≈ 3.30x  距爆仓 29.81%
  LIT  short config=  3x  实际≈ 3.26x  距爆仓 30.13%
  FIL  long  config=  3x  实际≈ 3.06x  距爆仓 32.14%
  SUI  long  config=  3x  实际≈ 3.04x  距爆仓 32.44%
  PEPE short config=  3x  实际≈ 3.03x  距爆仓 32.48%
  ETH  short config=  3x  实际≈ 3.01x  距爆仓 32.68%
  NEAR long  config=  3x  实际≈ 2.98x  距爆仓 33.08%
  BTC  short config=100x  实际≈93.63x  距爆仓  0.57%
  ARB  short config=  3x  实际≈ 2.03x  距爆仓 48.73%   ⚠️ 脱钩
```

`implied_leverage()` 是**估计量**：OKX 自己的爆仓公式用逐合约的维持保证金率（还含手续费），
我们假设统一的 `mmr=0.005`，所以 9 条腿里 `config=3` 反推出来是 2.98–3.30（±10%）、
`config=100` 反推 93.6（−6%）。**它只能当"粗脱钩"探测器（20% 阈值），不是精确读数。**

#### ⚠️ 我为了量这件事动了账户，必须交代

做对照实验时，**ARB 那条逐仓空腿从 3× 变成了 ~2×**（配置值已还原成 3，但持仓的
`margin` 停在 174.75、`liqPx` 停在 0.302064 ⇒ 实际 ≈2.03×）。这是"改配置不重算持仓"的
**副作用落地**：某一次写入落地时 OKX 重算了一次，之后就再没跟上。

- **方向上是变安全了**：距爆仓 **48.73%**，比原来的 32.83% 更远。
- **配置值已全部还原**：ARB `isolated = {long:3, short:3}`、NEAR `= {long:3, short:3}`、
  LINK `= {long:3, short:3}`、**BTC `= {long:100, short:100}`（未动）**。
- 要把它真正改回 3× 只能**平掉重开** —— 那是交易动作，**没有你的确认我不会做**。

#### 结论与建议

**统一设成 3× 治不了这个问题的根。** 真正的问题不是"逐仓杠杆没统一"，而是：

1. 这个账本是**对冲的**，而**逐仓会把它拆成 N 笔独立方向押注**（Q36：任意 `L≥1, G≤1` 下
   全仓 ≥ 逐仓；全仓账户级爆仓距离 **223%**，逐仓 BTC 那条 **0.57%**）。
2. 而且**对冲腿的盈利在逐仓下救不了另一条腿**，强平还会把对冲拆成裸方向仓。

所以建议的顺序（**都要确认，涉及动仓**）：

1. **先决定要不要保留逐仓。** 我建议**不保留** —— 把 `td_mode` 钉死成常量 `cross`、从控制台
   下拉里拿掉、让它落盘并进成交记录。这样 9 条逐仓腿会被并进全仓，"统一 3×"这件事直接消失。
2. 若坚持保留逐仓 → 修 `set_leverage`（补 `posSide` + 每合约两次 + 写完**等 ~60s 再用
   `liqPx` 反推复核**，不能信 `lever` 回读）。
3. **BTC 那条 100× 腿单独处理**：平掉重开，或直接加保证金。它现在距爆仓 **0.57%**。

### Q39. 控制台的三个可用性缺陷（2026-09-30 实测修复）

#### ① 「删除失败：`Unexpected token '<', "<!DOCTYPE "...`」—— 报错指错了方向

**根因是进程陈旧，不是删除逻辑。** 实测：

* 控制台进程 PID 9982 是 **09-29 18:51** 起的；
* `do_DELETE` 是 **09-30 00:46** 才进仓库的（commit `321a31d`）。

改过 `webapp/` 却没重启 ⇒ 进程里没有 `do_DELETE` ⇒ `BaseHTTPRequestHandler`
走 `handle_one_request` → `send_error(501, ...)`，回一张
**`Content-Type: text/html`** 的错误页：

```
HTTP/1.0 501 Unsupported method ('DELETE')
Content-Type: text/html;charset=utf-8

<!DOCTYPE HTML>
<html lang="en"> ... <p>Message: Unsupported method ('DELETE').</p> ...
```

而前端当时写的是 `const d = await resp.json()` —— 在这上面抛
`Unexpected token '<', "<!DOCTYPE "... is not valid JSON`。
**用户看到的是"JSON 解析失败"，真正的原因（服务端不支持 DELETE / 控制台没重启）
一个字都没露出来。**

两处都修了：

| 位置 | 改动 |
|---|---|
| `webapp/server.py` | 新增 `send_error()` 覆盖：`/api/` 下的**任何**错误（含未实现的方法）都回 JSON 信封；静态资源/页面仍走父类 HTML |
| `app.js::deleteRun` | 不再盲目 `.json()`：先 `resp.text()`，能解析就当 JSON，不能就报 `HTTP 501 + 服务端返回的不是 JSON`；501 直接点名「控制台多半没重启」 |

**通用教训**：`BaseHTTPRequestHandler` 对未实现的方法回的是 **HTML**，
所以「前端 `resp.json()` + 一个可能缺方法的服务端」= 一个把根因藏起来的报错。
契约必须是「`/api/` 的错误永远是 JSON」。

#### ② 交易台金额被取整，看不到「分」

`fmt.dol` 原来是 `'$' + Math.round(v).toLocaleString('en-US')` ⇒ `$2,586.98`
显示成 **`$2,587`**，看着像对上了，其实差 2 分。交易台上的净值 / 未实现 /
持仓名义 / 订单名义额全走这个格式化器。

改成两位小数；**唯一的例外是真·亚分钱**（`|v| < 0.005` 用有效数字）——
因为 `$0.00` 会**假装"这是零"**，比不显示小数更糟。

⚠️ 顺带修了一个**同类**问题：原来直接拼 `'$' + v.toLocaleString()`，
负数会变成 **`$-1,234.50`** —— 币种符号和负号打架。改成先取绝对值排版、再补符号
（`n < 0 ? '-$' : '$'`），并且 `-0` 仍然是 `$0.00`（不是 `-$0.00`）。

| 输入 | 旧 | 新 |
|---|---|---|
| `2586.9843` | `$2,587` | `$2,586.98` |
| `56441.303` | `$56,441` | `$56,441.30` |
| `875` | `$875` | `$875.00` |
| `0.004` | `$0` | `$0.00400` |
| `-1234.5` | `$-1,235` | **`-$1,234.50`** |
| `-0.0039` | `$-0.00390` | **`-$0.00390`** |
| `0` / `-0` | `$0` | `$0.00` |

#### ③ `START_*.command` 选错解释器 ⇒ `ModuleNotFoundError: No module named 'numpy'`

三个 `.command` 的候选表里写的是 `~/.workbuddy/binaries/...`，
**真正的托管路径是 `~/.workbuddy-ai/binaries/...`**（少一个 `-ai`）。于是它一路
回退到 `$(command -v python3)` = `/opt/homebrew/bin/python3` —— 那个解释器
**没有 numpy**。实测本机：

```
/Users/chenqifeng/.workbuddy-ai/binaries/python/envs/default/bin/python3   numpy 2.5.3  pandas 3.0.6
/opt/homebrew/bin/python3                                                  (没有 numpy)
/usr/bin/python3                                                           numpy 2.0.2  pandas 2.3.3
```

报错是 `import numpy` 处才炸，**完全指不到"解释器选错了"**。

**修法不是只改路径**：判据从「**可执行**」改成「**能 import numpy/pandas**」。
只改路径的话，下次路径再变会静默重现同一个坑；改成验依赖则当场说出来。
显式指定的 `PY` 也过同一道检查。三个脚本同步改，并 `chmod +x`
（原来都是 `-rw-r--r--`，双击根本不会执行）。

#### 复验（裸 socket，`curl` 在本沙箱说谎）

重启后的控制台（PID **30584**）实测：

把 ADV 门槛关掉（`min_avg_amount_usd=0`），两边横截面几乎一样宽（78.3 vs 80.0），结果**反过来**：

|---|---|---|
| 门槛开（$3M） | 1.929 | 1.334 |
| **门槛关** | **0.071** | **1.183** |
| 有效横截面（门槛开） | 16.1 | 38.7 |
| 有效横截面（门槛关） | 78.3 | 80.0 |

门槛开时 OKX 只有 **16** 个标的、币安 **39** 个 —— **两边根本不是同一个策略**，
而是同一个阈值在两套成交额刻度上筛出的两个不同宽度的横截面。

#### ⑤ 决定性实验：把门槛按**各自分位数**扫，横轴对齐到"实际筛出多少名"

三条结论：

1. **币安全程最高 1.494，够不到 OKX 的 1.942。** 换任何 ADV 门槛都够不到 ⇒
   验收口径的 1.94 **不是**"市场属性"，至少有一部分是 OKX 数据 + 这个阈值的组合属性。
2. **OKX 的 1.94 是尖峰不是平台**：左右邻居 1.184（宇宙 24.5）与 1.511（宇宙 10.2）。

   一个尖峰比一条平线更可疑 —— 它更像样本特性，不像结构。
3. **两家的共同点是：ADV 门槛本身极其重要。** OKX 关掉门槛 Sharpe 从 1.93 掉到 **0.07**。
   验收结果高度依赖**一个宇宙阈值参数**，这是比"换交易所"更值得警惕的脆弱点。

**顺便否掉了我自己的一个假设**：宇宙 16 个 vs `2×top_k = 20`，我怀疑长短名单会重叠、
尖峰是退化造成的。实测**每档重叠都是 0.00**（`select_book` 按分数正负分腿，构造上不可能重叠）。
假设不成立，尖峰是真的（尽管依然可能过拟合）。

#### ⑥ 分折看：门槛开时 15 折里币安只赢 3 折

| | test-Sharpe 相关 | 差值均值 | 币安更好的折数 |

* **换交易所不会推翻策略，但会推翻"1.94"这个数字。** 币安上是一个 Sharpe ~1.4、
  更平、回撤更大的版本。

  ② 每个交易场所各自校准；③ 至少把**有效横截面宽度**当作运行元数据落盘。
* **1.94 落在尖峰上这件事要单独交代。** 现有产物里没有任何东西记录"换一个 ADV 门槛会怎样"。

### Q41. 5 段最大回撤的**失效归因**（2026-09-30 诊断，**未做任何优化**）

问：5 个历史最大回撤窗口里**到底发生了什么**？是哪条腿、哪个因子、哪种状态失效的？

**硬约束（本阶段唯一目标 = 解释历史，不是改进策略）**：未调任何参数、未改因子权重 / 因子集 /
TopK / 止损 / 杠杆 / 换手限制、未加 regime filter、未优化进出场。
配置从 `config.settings.ACCEPTED_*` 读，存档在 `artifacts/drawdown_attribution/config.json`
（含 `"optimization_performed": false`）。**复现基线逐位一致**：重建面板后重跑，
9 个损益列 `max|Δ| = 0`。

#### 三个必须先说清的前提（否则下面的表会被读错）

1. **会计恒等式是 `net = gross − fee − spread − impact **+** funding`。**
   `funding` 是**带符号现金流**（`engine.py:433` 把它**加**进账），不是成本项。
   实测 `max|resid| = 8.7e-19`。**写成 `− funding` 会把每一笔资金费记成贷记** ——
   本样本全期 `funding = +0.0918`（策略净收资金费），减号会让整块成本分析反向。
2. **用户给的 5 个窗口不是同一套边界约定。** W1/W4/W5 = 峰→谷；**W2 的第二个数是恢复日**
   （真实谷底 2023-12-18）；**W3 的第一个数是回撤内部的局部高点**（真实 cummax 峰 2023-01-25）。
   5 个深度**逐位吻合**（`max|Δdepth| < 1e-4`）⇒ 是同一批事件，但切片定义不统一。
   因此**两种切片都报**：`stated`（对账用）与 `episode`（真实峰→谷）。
3. **W2 的 `stated` 窗口净收益是 +0.0188（正的）** —— 因为窗口延伸过了谷底。
   它的 −10.82% 是**峰→谷深度**，**不能**当成那 116 天的损益。只有 `episode` 才是 −0.1087。

#### 结论

| 根因候选 | 判定 | 关键证据 |
|---|---|---|
| **A 横截面动量反转** | **支持（同期状态描述），但无预测力** | momentum 回撤期 IC **−0.0378** vs 正常 **+0.0088**（块置换 p = **0.0095**）；4/5 窗口为负 |
| **B `flow` 因子失效** | **支持，且比 A 更稳健** | 回撤期 IC −0.0442 vs −0.0003（块置换 p = **0.0080**，五因子里最显著）；单因子 Sharpe 最低（0.50）、MDD 最深（−23.73%） |
| **C Short Leg 崩跌式反弹** | **部分支持；机制「证据不足 / 无法确认」** | `episode` 下 3/5 窗口由空腿驱动；但**没有**度量被空标的当期收益分布 |
| **D 流动性压缩** | **伴随现象 / 放大器，不是独立根因** | 4/5 窗口宇宙更窄（W4 仅 **7.4** 名）；但 `binding_adv` **恒为 0** |
| **E 交易成本** | **明确排除** | 5/5 窗口**毛收益本身就是负的**（`episode`）；成本只占毛亏损 6.7%–23.0% |

**Long vs Short（必须分口径答）**：`episode` 口径 **3/5 空腿驱动**（W1/W2/W4）、
**1/5 多腿驱动**（W5）、**1/5 两腿同亏**（W3）；`stated` 口径是 2/2/1。
⇒ 「失效是空腿问题」**错**（W3/W5 相反）；「是两条腿的问题」也**错**。

#### 动量反转：有数据支持；但**不能当择时信号**

### Q42. 「宇宙变窄」是不是一个可用的**事前**状态量？（2026-09-30，Q41 的事后补测）

问：Q41 发现 4/5 个回撤窗口的宇宙比正常期窄，但只把它写成「伴随现象 / 放大器」就停手了。
那等于**没检验就下结论**。这里把它当**可证伪的假设**来测。

**它为什么值得单独测**：是 Q41 里**唯一**同时满足三点的候选 —— ① 4/5 窗口都成立；
② **事前可见**（调仓那一刻就知道有几个名字）；③ 能挂上一个**具体机制**
（`cap × n ≤ 1` ⇒ `inverse_vol_weights` 静默退化成等权）。

#### 三个必须先处理的坑

1. **宇宙宽度有长期趋势**：与调仓点序号的 Spearman = **+0.398**（2021 年均 11.7 名 →
   2024 年 23.1 名 → 2026 年 13.1 名，**非单调**）⇒ 必须用**滚动百分位**（只用 t 之前 180 期）。
2. **未来损益也有趋势**（净值在涨）⇒ 除原始损益外还要看**滚动去均值**的版本。
3. **宽度 0 的调仓点**（实测 **13** 个）没有仓位、损益恒为 0 ⇒ 会把「窄 = 不亏」的假象
   喂进相关性。已剔除并显式报数。

#### 结论：**两个假设都被否定**

**① 事前宽度对下一期损益没有预测力。** 8 个组合（原始/去趋势 × 净/毛 × 原始宽度/滚动百分位）
的秩相关 |t| **全部 < 1**（最大 0.82）。按事前宽度百分位分 5 组：

| 分组 | 宇宙均值 | 净损益 | 去趋势净损益 | 胜率 |
|---|---|---|---|---|
| Q1（最窄） | 11.82 | **+0.0013** | +0.0003 | 51.9% |
| Q3 | 17.01 | **+0.0017** | +0.0009 | **57.8%** |
| Q5（最宽） | 21.64 | +0.0011 | +0.0001 | 51.9% |

最窄 − 最宽 = +0.0002（Welch p = 0.763，**块置换 p = 0.776**）。**最窄那组的损益是正的。**

**② `cap × n ≤ 1` 的静默等权真的发生了，但不造成损失。**
先在**真实账本**上确认机制（此前只有代码推断）：绑定组的权重离散系数 = **1.24e-17**
（精确等权），不绑定组 = 0.391。但绑定组的下一期损益**略好**：
原始 +0.0014 vs +0.0009（块置换 p = 0.413）；去趋势 +0.0012 vs −0.0001
（Welch p = 0.094，块置换 p = 0.060）—— **边缘更好，不是更差**。

⚠️ 由此**不应**得出「把 `max_weight_per_instrument` 调大让加权生效」：那是
**没有证据支持的参数改动**，而且会抬高单名权重上限（集中度风险）。

⇒ 只有 W1/W5 窄，**W3 其实宽**。**Q41 的 D（流动性压缩）从「伴随现象」降级为「没有证据」。**

### Q43. 空腿有没有被「崩跌式反弹」挤压？（2026-09-30，Q41 §十-1 的执行结果）—— **已否定**

**背景**：Q41 把「空腿被反弹挤压」写成「机制证据不足 / 无法确认」，因为它只度量了空腿的
**加权 P&L**，没有度量**被空标的的当期收益分布**。Q43 补上这个直接检验。

**为什么不能直接看「空腿亏了多少」**：做空一个上涨的市场必然亏钱。必须把三件事分开
（逐点恒等、相加精确）：

```
被空标的的收益 = 市场（池子均值） + 选股（等权：被空标的 vs 池子） + 仓位加权（市值加权 vs 等权）
```

**判「挤压」只看「选股」那一项**（`excess_select`）—— 它与池子同为**等权**口径。
⚠️ 拿 `市值加权 − 等权池子`（`excess_mw`）当判据是错的：两个口径不同，它在牛市里恒为负，
而且会把「空得最多的那几笔涨得最多」误记成「被挤压」。

**结果（`episode` 切片 —— 与分腿 P&L 同一段 bar）**

| 窗口 | 被空标的收益 | 市场 | 选股 | 加权 | Welch p | 置换 p | 大涨占比（空/池） |
|---|---|---|---|---|---|---|---|
| W1 | +0.00406 | +0.00195 | −0.00002 | +0.00212 | 0.246 | 0.417 | 12.4% / 14.1% |
| W2 | +0.00732 | +0.00678 | −0.00038 | +0.00092 | 0.729 | 0.731 | 13.3% / 15.9% |
| W3 | +0.00126 | +0.00138 | +0.00012 | −0.00025 | 0.336 | 0.377 | 11.7% / 11.2% |
| W4 | +0.01228 | +0.00971 | +0.00082 | +0.00174 | 0.503 | 0.258 | 18.3% / 20.3% |
| W5 | −0.00400 | −0.00521 | +0.00240 | −0.00118 | 0.137 | 0.077 | 8.9% / 11.1% |
| 正常期 | −0.00206 | −0.00002 | −0.00108 | −0.00096 | — | — | 13.1% / 13.4% |

**四条结论**

1. **选股效应在 5 个窗口全部不显著**（Welch p 0.14–0.73、块置换 p 0.08–0.73）；
   W1/W2 甚至是**负的** —— 被空标的比池子涨得**少**。
2. **「涨超 +5%」的占比在 4/5 个窗口低于池子** ⇒ 尾部**没有**更肥。
3. **空腿亏钱主要是「做空了一个上涨的市场」**：W2 的空腿亏损 −0.1271 里市场项 −0.1272
   （**100%**）；W4 的 −0.1323 里市场项 −0.0872（**66%**）。
4. **W1 是唯一例外**：市场项只有 −0.0025，而**仓位加权项 −0.0933** ——
   W1 的空腿亏损是「**空得最多的那几笔恰好涨得最多**」（**仓位集中度**），
   **不是**「被空的名字涨得多」。两者是不同的问题。

**亏损集中度**（`episode`，前 6 名占该窗口空腿净亏损）：W1 **142.7%**、W2 **86.0%**、W4 **85.1%**。

### Q44. 钉死 `cross` 之后暴露的**第三条**：`cur_sz` 跨保证金模式求和（2026-09-30，**只诊断，未修**）

**实测（demo 账户 2026-09-30 18:36，8 个合约并存且全部同向）**：

**后果（两条，都已按代码路径核实）**：

1. **逐仓腿永久冻结。** 订单恒带 `tdMode=cross`，只作用于全仓那条腿；引擎既不能加也不能减逐仓腿。
   而这 8 条逐仓腿恰是**爆仓距离最差**的那批（逐仓中位 **32.8%** vs 全仓中位 **4341%**）——
   与 Q36「逐仓对这个对冲账本是反的」是同一个池子。**钉死 `cross` 挡住了新增，没挡住存量。**
2. **两条分歧，取决于目标大小**（`tgt` = 目标张数，`cross`/`iso` = 两条腿现有张数）：

     ⇒ **订单被交易所拒**（`planner.py:199-203` 的 close 分支 `reduce_only=False`，挡不住），
     该标的**永远收敛不了**，每个调仓点重试一次。

**为什么这一轮不修**：修它要改**下单量**（`account()` 的聚合键，或把 `td_mode` 变成逐仓位的量），

### Q45. 「全仓会被插针，所以该用逐仓」——单标的插针容忍度实测（2026-09-30，**结论与直觉相反**）

**为什么测**：有人提出「全仓会被插针，改成默认逐仓」。这是个**可测**的前提，而且项目里现有的
压测**恰好没覆盖它** —— `41d_market_move_liquidation.csv` 压的是「**所有腿同时逆行**」（对冲整体失效），
**不是单标的插针**。两者的排序可以不同，所以先测再决定，不靠直觉。

**测法**（`scripts/wick_margin_modes.py`，只读，产物 `42_wick_tolerance.csv` / `42b_single_name_wick.csv`）：
单标的 `j` 被插针 δ，**其余腿不变**；逐仓看该腿自己的 `liqPx`；全仓用**账户级判据**
`NAV − |notional_j|·δ < 毛敞口 × mmr`（`mmr=0.005` ⇒ 维持保证金 ≈ **$120**）；
同时列出交易所自己给的 `liqPx` 作对照。

**实测（demo，NAV 55,348 / 毛敞口 23,903 = **0.4319× NAV**）**

| 模式 | 最近 | 中位 | 最远 | 有 `liqPx` |
|---|---:|---:|---:|---:|
| `isolated` | **26.03%** | 32.66% | 49.01% | 8/8 |
| `cross` | 385.03% | 4,344.89% | 13,128.37% | 5/12 |

**单标的插针扫描（只动一个标的，其余腿不变）**

| 插针幅度 | 逐仓被打掉的腿 | 全仓被打掉的腿 | 逐仓损失 | 全仓账户损失 |

**账户级判据**：全仓账户爆仓需要 **231.1%** 的同向移动（`(1−mmr·G)/G`）——
但那是**所有腿一起逆行**才需要的幅度，**单标的**不需要那么大。

⚠️ **初稿在这里犯了一个错，必须记下来**：我原本写「单个最大标的（$2,867）要 1,930% 才吃掉全部 NAV」

**空头才是无界的**。按空头重算（`打爆账户需要的涨幅 = NAV / 该腿名义`）：

| ETH（全仓） | $363 | 152.3 倍 |

⇒ **最脆弱的一条只要 30.7 倍**；「涨 100 倍」是 3 倍有余。**这一条推翻了上面「全仓更耐插针」的结论。**

**结论（一半对一半错 —— 见下面的更正）。** 就「**多久被强平一次**」而言，被插针打掉仓位的
是**逐仓**（26% 死第一条腿、50% **全死**），全仓要 385%–1,930%。差 **10–74 倍**。机理很直白：
逐仓每条腿只用自己的保证金（`1/L − mmr` = **32.83%** @ 3×），全仓用**整个账户权益**背书 ——
这正是 Q36 那条定理（任意 `L≥1, G≤1` 下全仓 ≥ 逐仓）在**单标的**情形下的表现。

⚠️ **但「多久被强平」不是全部**。上面这张表只回答了**频率**，没回答**损失有多大** ——
而后者才是决定性的。下一条更正把这个补上，并**推翻**本节的小结。

⚠️ **一处必须披露的不一致（未解释）**：交易所给 `LIT cross` 的 `liqPx` 隐含 **385%**，
而账户级模型对同一条腿说 **4,527%**（与全仓中位数 4,345% 吻合）。LIT 是异常值。
所以上表 400% 行的「1/12」是**交易所口径**，账户级模型判**未爆仓**。
**两个口径都指向同一结论**（全仓远更耐插针），但数字**不同源**，不能混用。

⚠️ **公平的另一面**：逐仓**单腿损失有上限**（爆仓即亏掉该桶保证金，实测最坏 $601/腿、
8 腿合计 $2,337），全仓理论上是**无限**的（账户爆仓则全部仓位一起被平）。
所以「怕账户归零」→ 逐仓；「怕被插针打掉仓位」→ 全仓。**但当前账本毛敞口只有 0.43× NAV**：
全仓那条路要 **231%** 才走得到，逐仓那条路 **26%** 就走到了。

⚠️ **口径提醒**：OKX 用**标记价**判爆仓，纯 last-price 插针未必传导到 `liqPx`；
这一点**两种模式一样**，不改变上面的比较。

**决定（2026-09-30，应要求）**：把 `settings.MARGIN_MODE` 从 `cross` **改成 `isolated`**。
依据是上面那条**尾部**：全仓下**空头的亏损没有上限**，单个合约暴涨会打爆**整个账户**
（最脆弱那条只要 **30.7 倍**）；逐仓把它封在**那一条腿**的保证金里。
这是**偿付风险**，比「多久被强平一次」更硬 —— 所以哪怕代价更大，也选它。

**代价必须一起报，而且它决定了杠杆**：逐仓的容忍度只有 `1/L − mmr`，所以**模式与杠杆必须一起动**。
按上面的实测：3× → 每年约 **30 次**强制平仓，2× → ~10，**1× → ~1**。
**⇒ 账本应按 1× 运行。** 3× 是账户当时恰好配置的值；而**降低杠杆不会给已在场的腿重新分配保证金**
（Q36），所以存量仓位必须**平掉重开**才生效。

**改了什么**
- `settings.MARGIN_MODE = "isolated"`（唯一来源，仍是一行）。
- 控制台标签改为**从服务端值派生**。它原来是写死的「全仓 cross」—— 常量一改，页面就会显示
  **与实际相反**的模式，而且属于「看着很正常」的那种错，肉眼扫过去不会发现。
- `test_margin_mode.py` 里三处把 `"isolated"` 当「冲突值」的测试改为从 `MARGIN_MODE` **派生**。
  ⚠️ 这条很关键：常量一翻，那些测试就**不再测试任何东西**却依然全绿（假守卫），
  和 Q43 里「挪一根 bar 不会红」是同一类。

**守卫**：**变异 4/5 被抓**（前端标签写死 / `_OTHER_MODE` 塌成同值 / 只读属性返回字面量 /
API 守卫拿字面量比）。**漏掉的第 5 条是「把常量翻回 `cross`」—— 这是刻意的**：测试断言的是
**性质**（唯一来源、只读、冲突被拒、标签跟随值），不是**取值**，与 `test_accepted_grid.py`
的「断言一致而非数值」同一条纪律。
**反向验证**：把常量翻回 `cross`，全量 **568 passed** + 冒烟**全部通过** ⇒ 这个开关是
**干净可逆的一行**，没有隐藏依赖。

⚠️ **落地后的实际状态**：demo 账户里还有 **12 条全仓腿 + 8 条逐仓腿**。模式翻成 `isolated` 之后，
引擎的订单会带 `tdMode=isolated` ⇒ **变成 12 条全仓腿动不了**（Q44 的镜像，不是新问题）。
存量仓位需要平掉重开，两种模式才能真正收敛到一种。
