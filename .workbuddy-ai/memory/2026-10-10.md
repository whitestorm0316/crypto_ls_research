### Q48：① 页面显示保证金占用/可用余额 ② 账户级「无人值守」开关（2026-10-10）

用户要求：①「可以」——即在页面上把保证金占用 / 可用余额显示出来（补上 Q47 暴露的缺口）；
②「每天11点刷新行情+下单，可以给账户设置开关做这件事」——把每日自动交易做成**账户级开关**。

**① 保证金显示（补 Q47 的缺口）**
- 新增 `OKXPrivate.margin_usage()`：读 `/account/balance` 的 `eq / isoEq / imr / availBal`，
  返回 `margin_used = isoEq + imr_cross`、`margin_frac`、`avail_frac`。
  **只取交易所字段，不做任何折算** —— Q47 试过拟合 `margin` 的闭式解，21 条腿对不上。
- `engine.account()` 增加**第三次**并发调用（`max_workers=2 → 3`），并在快照里加
  `margin` 与 `gross_notional`；读失败返回 `{"unavailable": True}`，**不让多读一项
  打坏原本能用的账户快照**。
- 页面新增 `marginCell()`，与「持仓名义」并排：`保证金占用 / 占净值 / 可用余额`。
  占比 ≥85% 红、≥65% 黄 —— 绑到「还剩多少可动」上，因为那才是可操作的约束。
- 实测：毛敞口 241.03、保证金 254.66、可用 102.63、占净值 71.3%。

**② 无人值守开关**
- 设计要点（都已钉成测试）：`enabled`（许可位，落盘）与 `running`（进程活着）
  **是两个量**，页面必须分开说 + 派生 `will_trade = enabled AND running`。
- **默认关，且方向是承重的**：`resolve_auto_enabled` 对**非 dict / 缺失 / 类型不对**
  一律 False。⚠️ 用 `is True` 而不是真值测试 —— `"false"` 在 Python 里是真值，
  用 `bool()` 会把开关**静默打开**（变异测试当场验证这条）。
- **每个 tick 重读**（不缓存）⇒ 页面拨开关立即生效。保证方式是把它排在
  `kill_switch_on()` 之后、**数据刷新之前**：关着时 `skip / auto_disabled`，
  实测 **0.0s**（连行情都不刷新）。"什么都不做"必须真的是什么都不做。
- **实盘开启要当日确认短语**（与手动下单同一个 `live_confirm_phrase`）；
  **关掉永不需要**。任何「停下来比开起来更难」的设计都是反的。
- 响应回**落盘后重读**的值，不回显请求 —— 回显会让写盘失败看起来像成功。
- 开关**不和心跳 `auto.json` 共用文件**（那个每轮被重写 48 次）；
  用 `auto_config.json`。
- API：`GET /api/live/auto`（返回 enabled/running/will_trade/config_path）、
  `POST /api/live/auto/{enable,disable}`。

**③ 三个我自己犯的错（都当场被抓）**

### Q49：把每日自动交易从「独立守护进程」改成「控制台内置调度」（2026-10-10）
用户问：「为什么还要开启守护进程呢，现在后端不是开着吗」——**他说得对**。
我核对后确认：控制台（8790）活着，但**它不是守护进程**；而页面文案写「它**不替代**
下面的『启动守护进程』」，措辞像两个按钮功能重叠，实际是缺一不可 —— 把人绕进去了。

**① 决定性事实：控制台本身就能当常驻者**
- 控制台是 `daemon_run.py` **双重 fork + setsid()** 起的，父进程是 launchd
  ⇒ **不受工具调用结束影响，能长期活着**。
- 而原来那条「守护进程」路恰有个老毛病（README §一·补）：从 Web 按钮派生的子进程
  会随调用方进程树被回收（日志断半句、无 traceback、`is_running()` 几秒后变 False）。
  实测 live/demo 的 pid 84741 / 9989 **都已死**。
- ⇒ 既然控制台一直在跑，**没必要再拉一个进程**。用户裁定：
  「后端内置定时器 + 启动时自恢复」，并且**去掉确认短语闸门**，就一个普通开关。

**② 实现**：新增 `webapp/auto_schedule.py`（Scheduler + Registry）
- `Scheduler`：线程每秒醒一次，`_maybe_run()` 依次判 **开关 → 到点 → 今天跑过没**。
- **走和网页按钮同一条路**：`auto_runner` 把「刷新行情 → 计划并下单」提交进
  **`live_api._submit` 的同一个作业队列**。不自己调 `engine.execute()`
  —— 那会变成"两个 actor 各读一遍同一本书、各发全量单"（`rebalance_lock` 只串行化
  单次调仓，两个循环会交替插入而非碰撞）。
- **启动自恢复**：`server.py::main` 调 `start_enabled_schedulers()`，读每个账户的
  开关、开着的自动建线程。没有它，"重启一次就再也不自动了"而页面仍显「已开启」。
- `_auto_view` 的 `running` 语义**换成调度线程**（不再是 `auto_ctl` 那个守护进程）。

**③ 五个必须守的性质（`test_auto_schedule.py` 13 条 / 变异 7/7 + 2/2）**
1. **关着 ⇒ runner 一次都不被调用**（只断言"结论里写了跳过"会放过"先下单再改结论"）。
2. **同一天只执行一次**（每秒醒一次，不记账就是每秒下一单）；**跨进程也幂等**
   （重启后同一天不该再来一次）。
3. **失败不写幂等账**（抖动=当天不交易是错的，要能重试）；**成功立刻记账**
   （重复提交=双倍下单）。
4. **错过不补**（见下）。
5. 线程 start 幂等、stop 之后不再活着。

**④ 🔴 我实现出来的 bug，当场被自己的测试和实测抓住**
- 第一版 `due()` 只判 **`now >= at`**。我把控制台在 **15:25** 重启时，它**立刻执行了一次**
  ——`runs.jsonl` 多出一条 `15:25:31 n=0`（恰好没下单，因为目标已与持仓一致，
  但**机制是错的**：任何下午的重启都会拿当天已过期的信号下单）。
- 改成**窗口**：`at <= now <= at + 10min`，超过就算错过、等下一个窗口。
  `_parse_hhmm` 解析失败返回 `None`（不是 0）⇒ 不执行，fail closed。
- ⚠️ **修完立刻连带打红 5 条我自己的测试**：fixture 用 `at="00:00"` 表示"恒到点"，
  加窗口后它落在窗外。改成 `at=一分钟前`（天然在窗口内）。
  ⇒ **"恒为真"的 fixture 要跟着语义一起改，否则测的是空气。**

**⑤ 连带的测试改动**
- `test_unattended_switch.py`：确认短语那条**反转**成「不再需要短语」（钉住这个决定，
  哪天有人加回来会红）；`running` 的 mock 对象从 `auto_ctl` 换成假 `Scheduler`
  （mock 错对象 ⇒ 断言测空气）。
- `smoke_live.js`：文案断言跟着改，并**新增一条**「开关文案不再提『启动守护进程』」
  —— 把用户指出的那句错话钉死。

**验证**：全量 **644 passed / 1 skipped**；`smoke_live.js` 全通过；控制台重启后
日志显示 `[ok] 每日调度：已恢复 (...)`；开关链路实测
`enable → enabled=True running=True will_trade=True` / `disable → False`。
