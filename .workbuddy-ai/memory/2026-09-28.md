## 解答「demo 下单金额为什么只有 $0.32」

用户下单成功 2 笔但名义额 $0，问"这对吗"。

**两笔订单的实际金额（我按 ctVal 核过，`notional` 字段算法是对的）**：

- **11 成交 / 8 被拒**。本地账本 `orders.json` 19 行**全部** `state=rejected`、

## 第三轮：风控限额保存了重启不生效 / 今日换手预算对不上

用户报两条：**「风控限额相关保存了 重启不生效」**、**「今日换手预算 也对不上」**。
两条都是真的，而且都属于「在一个进程内看不出来」的那类缺陷。

### 归因（都是读代码/读账本读出来的）

**① 保存没有落点。** `/api/live/limits` 只做 `eng.limits = lim` 然后回 `{"ok": True}`。
全仓库没有任何一处把限额写到磁盘；配置只活在 `live_api._ENGINES` 这个进程内缓存里。
于是「保存成功」与「按钮根本没接线」在同一个进程内**完全无法区分**，只有重启才暴露。
只读验证抓到了铁证：`curl /api/live/status?mode=paper` 里 `limits_saved: null` ——
用户说"保存了"，而磁盘上从来没有过这个文件。

**② 同一个界面上两个同名不同义的量。**
- 账户区「今日换手预算」= `turnover_budget`，来自信号参数
  `execution.max_daily_turnover`（v3 = 20%），是**策略节流**（决定每期执行目标变动的百分之几）；
- 限额表里的 `max_turnover_frac` = **硬闸门**，超过就整批拒绝，**不参与节流**。
两者数值都可能是 0.2 —— 看起来像同一个旋钮，而页面上两处都不说来源。

**③ 一个定义、两个调用点漂移。** `store.summary()` 读的是**原始**
`turnover_used_today`（不重置），而 `store.turnover_state()`（规划器据此下单）
按 UTC 日重置。日切之后面板显示昨天的用量、规划器按空预算下单：一个页面两个答案。

### 修法

- `store.py`：新增 `LIMITS_FILE = "limits.json"` + `load_limits()/save_limits()/limits_path()`。
  **故意不放进 `LEDGER_FILES`** —— 「重置纸面账户」会归档账本，那一刻顺手忘掉风控上限是最坏的时机。

### 顺带修掉的**真缺陷**：HTTP 200 不是结论

加飞书时查到：飞书的错误是 **HTTP 200 + 响应体 `code != 0`**（`19021` 签名失败、
`19024` 关键词不匹配、`19022` IP 白名单、`11232` 限流）。而原来的 `_dispatch` 是

飞书/Server酱 `code:0`、pushplus `code:200`（不是 0！）、企业微信 `errcode:0`。

- 用户给了飞书群机器人 webhook。`--set-url` 一次成功：`code:0 / success`，`ready:true`。
- **日志暴露了两个东西**。一个是好消息：热读取**真的生效了** ——

- 另一个是**真缺陷**：日志里是**完整明文 URL**。`redact()` 只处理 `?key=`，而
  **飞书把 token 放在路径里**（`…/bot/v2/hook/<id>`）→ 明文 token 被写进
  `logs/auto_demo.log` 与 `artifacts/live/demo/auto.json`，两个都是 **0644**。
  用户粘一个 URL 就泄漏一次。
- 修法：`redact()` 增加末段路径脱敏 `_looks_like_a_token()`（≥12 字符且含数字，或 ≥20 字符）

  顺带 `chmod 0600 logs/auto_demo.log`。清理了两个产物里的明文。
- **验证方式是 grep 产物**（不是读代码）：修完全仓只剩 `config/notify.json`(0600) 有明文；
  心跳里是 `…/hook/***`；控制台 API 也不回传。`--test` 真发一条成功 →
  证明**脱敏只影响显示**，传输层拿到的是完整 URL。
